# Section 3 - 3. 객체 타입의 호환성

**1. 객체 타입의 호환성**

객체 타입도 기본 타입처럼 **슈퍼 타입과 서브 타입 관계**를 기준으로 호환성을 판단한다.

```text
서브 타입 → 슈퍼 타입
→ 할당 가능

슈퍼 타입 → 서브 타입
→ 일반적으로 할당 불가
```

---

**2. Animal과 Dog**

```ts
type Animal = {
  name: string;
  color: string;
};

type Dog = {
  name: string;
  color: string;
  breed: string;
};
```

`Dog`는 `Animal`이 요구하는 모든 프로퍼티를 가지고 있다.

```text
Animal
├─ name
└─ color

Dog
├─ name
├─ color
└─ breed
```

따라서 `Dog`는 `Animal`의 **서브 타입**이다.

```ts
let animal: Animal = {
  name: "기린",
  color: "yellow",
};

let dog: Dog = {
  name: "돌돌이",
  color: "brown",
  breed: "진도",
};

animal = dog;
```

가능하다.

반대로는 불가능하다.

```ts
dog = animal;
```

`Animal`에는 `breed`가 있다는 보장이 없기 때문이다.

---

**3. 프로퍼티가 적은 타입이 왜 슈퍼 타입일까?**

TypeScript는 객체의 **구조**를 기준으로 타입을 판단한다.

`Animal` 타입은 다음 조건만 만족하면 된다.

```text
name이 string
color가 string
```

따라서 `breed` 같은 추가 프로퍼티가 있는 객체도 `Animal` 조건을 만족한다.

```text
Animal
┌────────────────────────────┐
│ name, color를 가진 객체      │
│                            │
│   Dog                      │
│   ┌─────────────────────┐  │
│   │ name                │  │
│   │ color               │  │
│   │ breed               │  │
│   └─────────────────────┘  │
└────────────────────────────┘
```

즉,

```text
Animal
→ 더 많은 객체를 포함
→ 슈퍼 타입

Dog
→ 조건이 더 많음
→ 서브 타입
```

이다.

---

**4. Book과 ProgrammingBook**

```ts
type Book = {
  name: string;
  price: number;
};

type ProgrammingBook = {
  name: string;
  price: number;
  skill: string;
};
```

`ProgrammingBook`은 `Book`의 모든 조건을 만족한다.

```ts
let programmingBook: ProgrammingBook = {
  name: "한 입 크기로 잘라먹는 리액트",
  price: 33000,
  skill: "reactjs",
};

let book: Book = programmingBook;
```

가능하다.

```text
ProgrammingBook
→ Book

서브 타입 → 슈퍼 타입
```

반대 방향은 `skill`이 보장되지 않으므로 불가능하다.

---

**5. 초과 프로퍼티 검사**

객체 타입에는 한 가지 특별한 규칙이 있다.

객체 리터럴을 타입이 지정된 위치에 **직접 작성하면 초과 프로퍼티 검사**가 수행된다.

```ts
type Book = {
  name: string;
  price: number;
};

const book: Book = {
  name: "한 입 크기로 잘라먹는 리액트",
  price: 33000,
  skill: "reactjs",
};
```

`Book` 타입에는 `skill`이 없으므로 오류가 발생한다.

```text
Book이 요구하는 프로퍼티
→ name
→ price

객체 리터럴
→ name
→ price
→ skill  ← 초과 프로퍼티
```

---

**6. 객체 호환성과 초과 프로퍼티 검사는 구분해야 한다**

다음 코드는 가능하다.

```ts
const programmingBook: ProgrammingBook = {
  name: "한 입 크기로 잘라먹는 리액트",
  price: 33000,
  skill: "reactjs",
};

const book: Book = programmingBook;
```

`programmingBook`은 이미 변수에 저장된 값이므로 일반적인 객체 타입 호환성을 검사한다.

```text
ProgrammingBook
→ Book의 모든 프로퍼티 보유
→ 할당 가능
```

반면 객체 리터럴을 직접 작성하면 초과 프로퍼티 검사까지 수행한다.

```text
객체 리터럴 직접 할당
→ 타입 호환성 검사
→ 초과 프로퍼티 검사

기존 변수 할당
→ 일반적인 타입 호환성 검사
```

---

**7. 함수에서도 동일하게 적용된다**

```ts
function printBook(book: Book) {}
```

객체 리터럴을 직접 전달하면:

```ts
printBook({
  name: "한 입 크기로 잘라먹는 리액트",
  price: 33000,
  skill: "reactjs",
});
```

`skill` 때문에 초과 프로퍼티 검사에서 오류가 발생한다.

하지만 이미 변수에 담긴 객체라면 가능하다.

```ts
printBook(programmingBook);
```

---

**8. 초과 프로퍼티 검사의 목적**

객체 리터럴을 직접 작성할 때는 오타나 잘못된 프로퍼티를 작성했을 가능성이 높다.

예:

```ts
type User = {
  name: string;
};

const user: User = {
  name: "홍길동",
  nmae: "김철수",
};
```

`nmae` 같은 실수를 빠르게 발견할 수 있도록 객체 리터럴에 더 엄격한 검사를 적용한다고 이해하면 된다.

---

**9. 핵심 구조**

```text
객체 타입 호환성
→ 필요한 프로퍼티를 모두 가지고 있는가?

프로퍼티가 더 많은 타입
→ 조건이 더 구체적
→ 서브 타입

프로퍼티가 더 적은 타입
→ 더 많은 객체를 포함
→ 슈퍼 타입
```

그리고 별도로:

```text
객체 리터럴 직접 사용
→ 초과 프로퍼티 검사 추가
```

---

**10. 핵심 정리**

* TypeScript는 객체의 구조를 기준으로 호환성을 판단한다.
* 필요한 프로퍼티를 모두 가지고 있다면 더 많은 프로퍼티가 있어도 호환될 수 있다.
* `Dog`는 `Animal`의 서브 타입이다.
* `ProgrammingBook`은 `Book`의 서브 타입이다.
* 객체에서는 **프로퍼티가 적은 타입이 더 넓은 집합이므로 슈퍼 타입**이 된다.
* 서브 타입을 슈퍼 타입에 할당할 수 있다.
* 반대 방향은 필요한 프로퍼티가 없을 수 있으므로 허용되지 않는다.
* 객체 리터럴을 직접 할당하거나 함수에 직접 전달하면 **초과 프로퍼티 검사**가 수행된다.
* 별도 변수에 저장된 객체를 전달하면 일반적인 구조적 호환성을 기준으로 검사한다.
* 핵심은 **`필요한 프로퍼티를 모두 가지고 있는가`와 `객체 리터럴 직접 사용 여부`를 구분해서 보는 것**이다.
